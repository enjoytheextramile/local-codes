What replay really means Replay is not a bug. It’s a feature.

Replay happens when:

Kafka allows replay because:

5. hardware side -



Why disk is not the bottleneck here

Kafka does:

Sequential appends (no random writes)
Uses OS page cache
Avoids fsync on every message

So in practice:

Writes go to memory (page cache)
Flushed to disk asynchronously
Reads often served from cache

This is why Kafka can do millions of msgs/sec.

❌ Traditional DB:

random reads/writes
indexes
locks
fsyncs



3️⃣ Append-only log = performance gold

Kafka never:

updates messages
deletes individual messages
seeks randomly on write path

Flow:

Producer → append to log → OS cache → disk later

This is insanely cache-friendly.



This is a very good follow-up. You’re basically asking:

“What exactly does append-only buy Kafka, and what would the alternative cost?”

Let’s go deep and concrete.

1️⃣ What “append-only log” really means (mechanically)

Append-only log =

Every new message is written only at the end of a file
No updates
No deletes in place
No reordering
No random seeks on the write path

So, the write pointer always moves forward.

| msg1 | msg2 | msg3 | msg4 | msg5 | --> append here

4. Now the star: Sequence Numbers

Each record stored in a shard gets a sequence number.

Key properties:

Assigned by Kinesis, not producer
Monotonically increasing within a shard
Not contiguous
Meaningless across shards

Think of it as:

“offset-like, but shard-scoped and opaque”



Consumers don’t read by offset index like Kafka.

They read using iterators.

Iterator types:

TRIM_HORIZON

start from oldest retained record

LATEST

start from new incoming records

AT_SEQUENCE_NUMBER

start from this exact sequence number

AFTER_SEQUENCE_NUMBER

start after this sequence number





6. Checkpointing (critical difference from Kafka)

Kafka:

offsets stored inside Kafka
per consumer group

Kinesis:

checkpoints stored outside the stream
usually in DynamoDB (via KCL)
or managed implicitly (Lambda event source mapping)

Checkpoint = { shard_id → last_processed_sequence_number }

If consumer crashes:

it restarts from last checkpoint
anything after → reprocessed

👉 This is why duplicates happen.

Because checkpoint update is not atomic with processing.

5. The fundamental tradeoff triangle

You always choose 2:

Low latency
High accuracy
Low cost

Batch chooses:

accuracy + low cost

Streaming chooses:

low latency + acceptable accuracy

Why late events happen

network delays
retries

shard / partition lag







6. Practical handling strategy (real systems)

Most real pipelines do this:

1. Accept at-least-once delivery

2. Use event time + watermarks

3. Allow bounded lateness (e.g., 5–10 minutes)

4. Deduplicate by event_id

5. Correct downstream results if needed

6. Periodically reconcile with batch
